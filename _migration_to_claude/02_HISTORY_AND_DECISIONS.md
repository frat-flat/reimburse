- **変更指示**: アプリケーション名を『TaTekæTa』（タテカエタ。発音記号・合字æを適用）に変更。
- **決定事項**:

### ② モバイルUI/UXのモダン刷新
- **初期仕様**: PCブラウザ向けの横長テーブル中心のUI。スマホでは幅不足により文字重なりや改行崩れが発生していた。
- **変更指示**: 「スマホのUIがあまり綺麗ではないので、スマホのUIも洗練されたデザインにしてください。」
- **決定事項**:
  - カード型のレスポンシブレイアウトを全面導入。
  - スマホ向けに右側からスライドインするハンバーガードロワーメニュー（`MobileDrawerNav`）を実装。
  - アイコンをアウトライン線画（Lucide: strokeWidth 1.8）で統一。
  - Android PWAホーム画面追加時の白余白を解消するため、ダークネイビー背景のマスカブルアイコンおよび `manifest.ts` を設定。

### ③ 新規イベント作成の配置（インライン ➔ フローティングFAB & モーダル）
- **初期仕様**: ダッシュボードの画面中央上部に「新しいイベントを作成」フォームが常時表示されていた。
- **変更指示**: 「スマホでは、新しいイベントの作成画面が常時表示されていると邪魔なので、電卓のうえに鉛筆マークから新規イベントの作成ができるようにしてください」
- **決定事項**:
  - スマホ表示時はダッシュボード上のインライン作成フォームを非表示（`hidden lg:block`）化。
  - 画面右下のフローティング電卓（`bottom-5`）のすぐ上（`bottom-20`）に鉛筆マーク（✏️）のFABを配置。
  - 鉛筆マークタップでアニメーション付きの新規イベント作成モーダル（`CreateProjectModal`）が開き、ベースクルーの一括選択を含めて快適に入力可能にした。

### ④ 領収書の仕様決定・印鑑固定・フルカスタマイズ
- **決定経緯 1（印鑑移動のロック）**:
  - **初期仕様**: 領収書プレビュー画面でいつでも印鑑をドラッグ移動できた。
  - **変更指示**: 「発行された領収書は印鑑が動かせるようになっています。発行者側が領収書発行時の配置を決めるための機能であり、発行後も動かせるのはおかしいです。」
  - **決定事項**:
    - 発行済み（`status === 'receipt_issued'`）の領収書、および受け取り側（支払者）が閲覧する領収書は `readOnly={true}` に設定し、印鑑位置・透過度・設定項目を完全ロック。
    - 発行前の雛形作成時（マイページおよび発行直前の確認）のみドラッグ調整を許可。
- **決定経緯 2（但し書き・消費税）**:
  - **変更指示**: 「但し書きは、イベント「〜」の参加費としてにしてください。また、消費税も込みにしてください。」
  - **決定事項**:
    - 但し書きのデフォルトを `但し、イベント「${projectName}」の参加費として、正に領収いたしました。` に設定。
    - 領収金額に対する消費税（10%標準税率、税抜金額・消費税額）の内訳表示を自動計算して掲載。
- **決定経緯 3（領収書項目の自由編集）**:
  - **変更指示**: 「領収書はデフォルトで設定されていて構いませんが 消費税の10% 8%や正し書き または 相手宛名 日付 金額等々は編集はできるようにしておいてください」
  - **決定事項**:
    - `ReceiptModal` 内に「領収書の内容をカスタマイズする」アコーディオンを実装。
    - 相手宛名、領収金額、発行日付、但し書き、消費税率（10% / 8% / 非課税）を自由に編集可能にし、リアルタイムに紙面プレビューへ反映。
- **決定経緯 4（全イベント横断の領収一覧）**:
  - **変更指示**: 「領収書が発行されているのに、領収書一覧に反映されていません。発行された領収は受け取った領収書にはいるようにしてください。」
  - **決定事項**:
    - 専用ページ `/receipts` を作成。
    - 「受け取った領収書」（自分が支払った精算取引）と「発行した領収書」（自分が受け取った精算取引）をタブ切り替えで全イベント横断で確認・印刷できるUIを構築。

### ⑤ 通知システム（ベル通知・詳細閲覧・メール配信）
- **変更指示 1**: 「既に領収書を発行していた件について、修正があったため再度領収書の発行をする旨を通知してください。通知ボックスをメニュー内にベルのマークで作り、通知しておいてください。mate申請や承認、領収書の発行や受取の確認ができたら、また運営からこういったシステムの修正やアップデートも含めて誰から何の通知が届いたかが通知されるようにしておいてください。」
- **変更指示 2**: 「通知 ボックスができたが 実際にその通知が来ているものをタップしても どこにも飛ばず 本文が全て見えるところがありません 本文が見えるところを作成してください」
- **変更指示 3**: 「通知は登録メールにも届くようにしておいてください。」
- **決定事項**:
  - **通知データモデル（`Notification`）**: 受信者、送信者、種別（SYSTEM, MATE_REQUEST, MATE_ACCEPTED, SETTLEMENT_PAID, RECEIPT_ISSUED, RECEIPT_REISSUE_REQUEST, PROJECT_SHARE）、タイトル、本文、リンクURL、既読フラグを保持。
  - **アプリ内UI**: ヘッダーのベルアイコン ➔ 未読バッジ ➔ タップでドロップダウン ➔ アイテムタップで全文表示モーダル ＆ 関連画面へのジャンプボタン。
  - **専用通知ページ**: `/notifications` で全履歴を閲覧・一括既読可能。
  - **HTMLメール自動配信**: Resend API連携により、通知作成と同時に登録メールアドレス（`User.email`）宛てにブランドヘッダー付きのレスポンシブHTMLメールを送信。

### ⑥ パフォーマンス最適化 & ボタン操作レスポンス
- **変更指示**: 「とにかく操作から挙動までのラグが長すぎる」「ボタンに反応がなあくなっているのか見当もつかないぐらい反応がないですが」「何がそんなに遅くなっている原因ですか？」
- **特定された原因と決定事項**:
  1. `prisma.ts` の `connection_limit=1` を `10` に拡張（並列クエリの直列順番待ちを解消）。
  2. `auth.ts` の `getCurrentUser` を React `cache()` でメモ化（同一リクエスト内での重複DBクエリを完全排除）。
  3. 各画面（Header, Dashboard, プロジェクト詳細, 領収書一覧, Mate管理）のクエリを `Promise.all` で一斉並列実行。
  4. 支出保存時の `window.location.href` を Next.js の `router.push` に置き換え、画面全体の白画面リロードを全廃。
  5. ベースクルー・メンバー管理に 0ms 楽観的UI更新を導入。
  6. 精算ステータスボタン（`SwipeStatusButton`）がスライドドラッグのみにしか反応しなかった問題を改修し、**ワンタップ/クリックでも即座に状態が切り替わる**ように改善。
  7. 主催者（幹事）による全精算ルートの代理ステータス更新権限を解放。

## 2. 外部サービス・ライブラリに関する決定
- **データベース**: PostgreSQL (Supabase)。
- **ORM**: Prisma 6（`binary` エンジン）。
- **メール配信**: Resend（公式SDK `resend`）。`RESEND_API_KEY` 未設定時でもアプリ動作を中断させない安全フォールバック（コンソールログ出力）を徹底。
- **スタイリング**: Tailwind CSS v4。

## 3. 「こうしてはいけない」という厳格な制約
- **領収書の改ざん可能状態の放置**: 発行済みの領収書や受取人側の画面で印鑑や金額を動かせる状態にしてはいけない。
- **全画面リロード（`window.location.href`）の利用**: React/Next.jsのSPA状態を破棄してアプリ全体を再読み込みさせてはいけない。
- **外部サービス連携によるブロッキング**: メール送信などの外部ネットワーク通信が失敗しても、メインの精算・DB更新処理をエラーで巻き戻してはいけない（エラーセーフ設計）。
- **推測による勝手な仕様変更**: ユーザーが明示した文言・デザイン・業務ルールをAIの独断で変更してはいけない。
